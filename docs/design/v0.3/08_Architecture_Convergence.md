# ZZPing v0.3: Architecture Convergence & Data Integrity

- **Status:** Authoritative Specification
- **Date:** November 2025
- **Context:** This document defines the architectural vision for the data persistence, compression, and crash recovery
  mechanisms of ZZPing v0.3. It supersedes previous assumptions about `MemDB` responsibilities.

---

## 1. The Core Separation: Hot vs. Cold Tiers

The architecture splits data responsibilities into two distinct, autonomous Actors to separate **Ingestion/Networking**
from **Persistence/Compression**.

### A. `zzmem-db` (The Hot Tier)

- **Role:** The "Inbox".
- **Responsibility:** High-speed ingestion, network synchronization, and buffering.
- **State:** Volatile RAM. Holds **Uncompressed** `PingResult` structures.
- **Behavior:**
  - Receives data from Pinger (Collector) or Network (Database).
  - Organizes data into Ring Buffers.
  - Handles the "Rewind" protocol to fix network gaps using cached state.
  - Flushes aged/full chunks to `zzstorage`.

### B. `zzstorage` (The Cold Tier)

- **Role:** The "Archivist".
- **Responsibility:** Sharding, Compression (ANS), Disk I/O, File Finalization, and Historical Retrieval.
- **State:** Durable Disk (Production) or Heap (Test). Holds **Compressed** blobs.
- **Behavior:**
  - Receives raw, unified batches from `zzmem-db`.
  - Shards data by Target and compresses them using the v2 format.
  - Appends to daily log files (`.zz`).
  - Serves historical queries via the "Relay" mechanism.

## 2. The Storage Engine (`zzstorage`)

This component encapsulates all "Heavy I/O", sharding, and compression logic.

### 2.1. Thread Isolation (The Bulkhead)

To satisfy **Architectural Standard #4**, the `StorageActor` acts as a bulkhead against disk latency.

- **Execution Context:** The `StorageActor` **MUST be spawned on a dedicated `Arbiter` (OS Thread)**. It communicates
  with the rest of the system exclusively via async channels.
- **Isolation:** This ensures that even if `std::fs` blocks for seconds (e.g., spinning disk spin-up), the Network
  Reactor and `MemDB` remain responsive.
- **Hermeticity:** The actor supports an `ephemeral: bool` configuration. In ephemeral mode, it writes to `Vec<Vec<u8>>`
  in the heap, ensuring the compression logic is verified by tests without touching the filesystem.

### 2.2. Compression Format v2 (Nanosecond Precision)

The storage format upgrades the legacy `chunked_v1` logic to support higher precision and richer error states.

**The Data Structure:**

```rust
pub struct PingResult {
    pub target: String,
    pub sent_time_ns: u64, // UNIX Epoch Nanoseconds
    pub status: PingStatus,
}

pub enum PingStatus {
    Success(u64),       // RTT in Nanoseconds
    Timeout,            // 100% Packet Loss
    IOError,            // Network Unreachable, Permission Denied
    Partial,            // Orphaned Record (Sent but result never received before flush)
    Skipped,            // Interval skipped for flow control
    Other,              // Future-proofing
}
```

**Semantics of `PingStatus::Partial`:** This is an **Orphaned Record**. It is generated by the Database's `zzmem-db`
(Hot Tier) when a `Sent` event exists in the buffer, but its corresponding `Result` was not received before the chunk
flush deadline (e.g., due to a Collector crash or restart). We store it to preserve the 'Attempt' history without
falsely recording a 'Timeout'.

**The Symbol Map (ANS):** We utilize the upper range of the `u16` symbol space for error codes.

| Symbol       | Meaning                                           |
| :----------- | :------------------------------------------------ |
| `0`..`65529` | **RTT** (Logarithmic quantization of nanoseconds) |
| `65530`      | **Other**                                         |
| `65531`      | **Skipped**                                       |
| `65532`      | **Partial**                                       |
| `65533`      | **IOError**                                       |
| `65534`      | _Reserved (ANS Dummy)_                            |
| `65535`      | **Timeout**                                       |

### 2.3. File Finalization ("FSCK" on Startup)

The storage format is append-only. If the power is cut, the file exists, but the Header (which stores index offsets and
counts) will reflect the state at the _last flush_, not the _last write_.

- **Startup Routine:** `StorageActor` scans the tail of the active `.zz` file.
- **Logic:** Read sequentially from the last known good offset. Identify valid blocks. Rebuild the in-memory Index and
  update the Header on disk.
- **Why:** Without this, the last ~1 minute of data before a crash is permanently unreadable.

### 2.4. The Relay Feature (Client Symmetry)

To optimize historical queries, `zzstorage` acts as a specialized CDN.

- **Architecture:** The Client (GUI) imports the `zzstorage` crate. It shares the exact same decompression logic as the
  server.
- **Protocol:** `GetCompressedChunk { ... }`
- **Behavior:** The Database reads the **Compressed Bytes** from disk and sends them over the network _without
  decompressing them_.
- **Benefit:** This offloads the CPU cost of decompression to the Client and reduces network bandwidth usage by ~10-20x.
  Protocol symmetry is maintained.

## 3. The Buffer Engine (`zzmem-db`)

### 3.1. Unified Stream Architecture

To match **Axiom 3 (Unified Stream)** and the Pinger/Network wire formats, `MemDB` maintains buffers per-Collector, not
per-Target. Sharding happens only at the Flush boundary.

```rust
struct MemDBState {
    // Keyed ONLY by CollectorID. The value is a unified stream of all targets.
    // This maintains strict temporal ordering of events as they arrived from the wire.
    buffers: HashMap<CollectorID, RingBuffer<PingResult>>,
}
```

### 3.2. The Rewind Protocol (Desync Handling)

We handle network gaps and crash recovery using a handshake that relies on cached RAM state, strictly avoiding disk I/O
in the network path.

**The Lifecycle:**

1. **Application Boot:**

   - `zzstorage` initializes and runs Finalization.
   - It scans the tails of the logs to determine the "High Water Mark" (highest timestamp successfully persisted) for
     each Collector ID.
   - It pushes this `last_persisted_ts` map to `zzmem-db`.
   - `zzmem-db` caches this in RAM.

2. **Runtime (Flush):**

   - `zzmem-db` sends a `StoreBatch` message containing the unified stream to `zzstorage`.
   - `zzstorage` shards the batch by Target, compresses, and writes to disk.
   - **Atomic Success:** Only if all shards succeed does `zzstorage` confirm the new `last_persisted_ts` to `zzmem-db`.

3. **Connection Handshake:**

   - Collector connects.
   - Database `MemDB` looks up `last_persisted_ts` from **RAM** (Instant access).
   - Database sends `Handshake { last_persisted_ts }`.

4. **Reaction (Collector Side):**
   - The Collector looks at its unified Ring Buffer.
   - **Case A (Overlap):** If `buffer.tail < last_persisted_ts`, we reset the read cursor to `last_persisted_ts + 1`.
     This "rewinds" the stream and re-sends any data that might have been lost in the Database's RAM during a crash.
   - **Case B (Gap):** If `buffer.tail > last_persisted_ts`, the data is gone (overwritten in the ring). We send from
     `buffer.tail` (accepting the gap).

## 4. The Execution Engine (`zzpinger`)

### 4.1. Handoff Timing (Wall Clock Alignment)

We rely on `TokioAlignedClock` to ensure that a new Primary picks up exactly where the old one left off. Because slot
calculation is based on `UNIX_EPOCH % interval`, two independent processes on synchronized clocks will agree on the slot
boundaries without communication.

### 4.2. ICMP Identifier Rotation

To prevent data corruption during the transition period (where late packets from the Old Primary might arrive at the New
Primary):

- **Constraint:** The ICMP Echo Request contains an `Identifier` field (u16).
- **Logic:** When `zzpinger` receives the command `Enable(Primary)`, it must generate a **New Random Identifier**.
- **Effect:** Any late-arriving packets from the _previous_ session will carry the _old_ Identifier. The kernel (or the
  Pinger's raw socket filter) will naturally distinguish them.
